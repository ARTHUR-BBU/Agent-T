**<sub><sub>![P1 Badge](https://img.shields.io/badge/P1-orange?style=flat)</sub></sub>  Preserve source_subject_key through verify serialization**

`source_subject_key` is added to `q_payload` here, but `ConfirmQuestion` has no such field, so Pydantic drops it at `ConfirmQuestion.model_validate()` and it is absent from `VerifyInfo.model_dump()`. Consequently, when two `rule_attention` or `blind` questions refer to the same evidence but different source objects, `annotate_review_claims()` receives an empty subject key for both and emits the same `claim_id`, defeating the intended identity separation.

=== id=4074628556 app/graph/pipeline.py:409 ===
**<sub><sub>![P1 Badge](https://img.shields.io/badge/P1-orange?style=flat)</sub></sub>  Re-annotate verify questions written after the pipeline completes**

This annotation pass runs only when the initial review pipeline returns. A later `POST /api/review/{id}/verify` replaces `store.verify`, and re-verification replaces a question's evidence, but neither write path reruns claim annotation; their `/verify`, `/confirm`, and `/reverify` responses use `pack_verify()` directly. Thus newly generated questions expose blank claim fields, while rechecked questions can expose a `claim_id` and `evidence_refs` still derived from their pre-recheck evidence, until a separate `/review/{id}` GET happens to derive a corrected response copy.

**<sub><sub>![P2 Badge](https://img.shields.io/badge/P2-yellow?style=flat)</sub></sub>  Serialize content fields in the documented fixed order**

The `cc1` format defines a per-claim-type fixed field order, but sorting dictionary keys serializes quality observations as `comment=...` before `title=...`, rather than the specified `title` then `comment` order. Any client or audit tool that reproduces the documented byte-level algorithm will calculate a different `claim_content_hash` for every quality observation, so those hashes cannot be used reliably for cross-system drift detection.
