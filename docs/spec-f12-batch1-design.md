## 二、逐项设计

### ① F-2 豁免门（config/checklist_procurement.yaml breach 条目，class: hardline）

现病灶正则：`免除违约责任|免除.{0,8}违约`（yaml:204）——两个 bug：
- 「**不**免除其违约责任」（加责）命中「免除.{0,8}违约」（建设施工 17.4 实锤）
- 「**任何一方**…不承担违约责任」（对等免责）命中「不承担违约」（财政部 18.2 实锤）

修法（双层豁免，均走 unless 机制，不改 need_attention 主模式、不改 hardline 定级、不改 note 文案）：

```
unless:
  # 第一层：否定语境豁免（命中词处于否定前缀 → 一律不触发）
  - "不免除|不得免除|不视为免除|并未免除|不免责"
  # 第二层：对等量词豁免门（双重条件压进组合正则——对等量词与免责事由
  # 同句共现，句号内交叉匹配，等效老钱「邻域限定+免责事由限定」）
  - "(任何一方|双方均?|各自|彼此)[^。]{0,120}(不可抗力|情势变更|政府行为|自然灾害|疫情|法定免责)"
  - "(不可抗力|情势变更|政府行为|自然灾害|疫情)[^。]{0,120}(任何一方|双方均?|各自|彼此)"
```

- 邻域口径：句号边界（`[^。]`）内共现，等效 ±300 字符邻域但更严——**不做全文级豁免**（真单方条款召回保护：主体特定写法不含对等量词，照旧必中）
- 施工时以变异验证校准窗口长度（120 可调 60~200），红→绿双向实证
- 三清单（procurement/lease/nda）如有同构 breach 条目，同改（施工时逐一核对）

### ② 价款/期限 pass 语义域

**payment pass**（yaml:168-172）新增两条语义域模式（老钱 §二.1 收窄口径）：

```
# 语义域 A：标的词 ∧ 给付动作同句
- "(价款|货款|报酬|服务费用?|租金|对价|合同总价|合同金额|结算)[^。]{0,40}(支付|付款|付清|结清|支付给)"
- "(支付|付款|付清|结清|支付给)[^。]{0,40}(价款|货款|报酬|服务费用?|租金|对价|合同总价|合同金额|结算)"
# 语义域 B：金额兜底（限定语境，不单独成立——外审 P2）
- "(价款|总价|合同金额|费用)[^。]{0,20}(人民币|元)|((支付|付款|付清|结清)[^。]{0,30}(人民币|\\d+\\s?元))"
```

- 现有四条（质保金/验收合格后支付/分期支付/验收后付款）保留不动
- 裸金额不放行：违约金/责任上限/注册资本等金额不满足 A/B 任一语境组合
- 风险模式照旧：背靠背 hardline、一次性付清 heuristic 及其 unless 全部不动

**term pass**（yaml:181-187）新增存续期语义域（老钱 §二.2）：

```
- "合同期限|履行期限|交付期限|供货服务期|供货期|服务期|有效期|租赁期限|租期|工期"
- "自[^。]{0,15}日?起[^。]{0,15}至[^。]{0,15}止|自[^。]{0,15}至[^。]{0,15}止"
```

- 现有交付口径四条保留；not_found 模式不动

**不做**：subject_matter pass 扩展挂第二批（老钱 §三）；NDA 知产词表挂独立小批。

### ③ 签署等价组扩两行（三份清单 signature 条目）

lease yaml:429-436 已有等价组（15 份真实合同实证），**procurement/lease/nda 三份统一补**：

```
- "法定代表人[:：]"
- "授权代表[:：]|委托代理人[:：]"
```

- 语义：盖章栏 + 法人落款行（落到有签字权的自然人）= 完整签署配置（民法典 490 三选一等价，同租赁裁决二）

- 本批**不加**「空白模板」报告层旗标（老钱挂在明示不修+旗标项，随第二批报告层改动一并做，避免本批碰渲染层）

## 三、权力边界声明（本批不新增任何 LLM 权力）

本批是**纯规则工程**（YAML 词表/正则），不触碰 LLM 层。现有四层语义候选通道的边界维持宪法口径：

| 通道 | 现状 | 本批 |
|---|---|---|
| model_review（预审分诊） | 分类≠裁判，永不改档位 | 不动 |
| blind_spot（补盲候选） | 候选线索，需人工确认 | 不动 |
| quality（质量观察） | 参谋不计分，needs_confirm 代码强制 | 不动 |
| objection（异议） | 永不改当次档位，采纳=提案 | 不动 |

**规则正式结果 vs 模型语义候选**：档位（通过/需关注/未找到/不适用）唯一来源是规则引擎+人工决定记录（2c）；LLM 四层只产候选与解释。本批修复的是规则引擎自身的词表，与语义候选通道零耦合。

## 四、指标与闭环（语义候选 → 证据核验 → 人工确认 → 规则修复 → 金标回归）

修复效果与语义候选质量用以下指标持续度量（跑道扩展，随本批施工一并落 tools/m65）：

| 指标 | 定义 | 度量点 |
|---|---|---|
| 候选召回率 | 金标坐实条款被系统任一层发现的比率 | analyze_f12 复测：坐实 19 条修复后「未找到→通过/需关注」覆盖率 |
| 真实证据命中率 | 系统判项带真实原文证据的比率（evidence verified 占比） | run_eval §Q2 既有指标（claim_id 率 + verified 分布） |
| 误报率 | 需关注项中经金标/人工判为非风险的比率 | analyze_f12 F-2 判定 + 人工抽检标注 |
| 人工采纳率 | 人工决定记录中 confirm vs dispute 比率 | 2c 决定层（DecisionInfo）生产数据回流 |

闭环即本次已走过的路，固化为标准流程：**真实合同实测发现嫌疑 → 原文证据核验（验尸/分析器）→ 金标裁决（老钱）→ 人工确认批次与口径 → 规则修复（设计稿过审后施工）→ 金标回归（对抗断言 + 17 份真实合同重跑）**。
