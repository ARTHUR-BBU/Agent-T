# Agent-T Constitution / Agent-T 宪法

> **状态：规范性工程治理文件（Normative）**  
> **适用范围：Agent-T 的规则、AI、证据、工作流、数据状态、测试、代码审查与发布流程**  
> **核心原则：规则负责裁决，AI 负责质疑，证据负责约束，程序负责制衡，人工负责最终责任。**

---

## 序言：我们为什么需要一部“宪法”

Agent-T 表面上是一个合同审查应用，但它处理的不是普通内容生成，而是一个更敏感的问题：

> **系统凭什么把某句话称为“事实”，凭什么把某个事实称为“风险”，谁可以提出不同意见，又是谁有权改变正式结论？**

如果这些问题没有制度化答案，多 Agent 很容易退化成“几个模型轮流聊天”：每一层都能重新理解原文、重新发明证据、重新改写结论，最后没有人知道哪个对象才是事实、哪个状态才是正式结果。

因此，本文件不是品牌文案，也不是普通架构说明。它是 Agent-T 的**权力边界与工程治理基本法**。

所有新增功能、重构、Rule Pack 修改、Prompt 修改、Agent 增权、证据结构调整、流程节点变化，都应先回答：

1. 它属于司法系统中的哪个角色？
2. 它获得了什么权力？
3. 它明确没有什么权力？
4. 谁能监督、否决或纠正它？
5. 它改变正式结果时，证据与程序是否完整？

---

# 第一章：基本原则

## 第一条：事实、主张、裁决分离

Agent-T 必须区分至少三类对象：

- **Fact / Evidence：事实与证据** —— 合同里实际写了什么、位于哪里、来自哪个版本。
- **Claim / Argument：主张与论证** —— 某个事实可能意味着什么、为什么值得质疑。
- **Decision / Status：裁决与正式状态** —— 系统依据确定规则形成的正式核查结果。

任何实现都不得因为数据结构方便，而把三者混成一个不可追溯的字符串。

## 第二条：确定性裁决优先于生成式裁决

正式 Rule Result 应尽可能由**明确、可测试、可复现**的逻辑产生。

LLM 可以：
- 发现疑点；
- 提出异议；
- 补充上下文；
- 生成解释和修改建议；
- 帮助发现 Rule Pack 的盲区。

LLM 不得仅凭一次生成直接：
- 修改 Rule Result；
- 修改 Rule Pack；
- 修改适用条件；
- 将未验证内容提升为正式事实；
- 将自身意见写成“系统已经确认”。

## 第三条：证据优先

任何影响风险判断的重要主张，都应尽可能回答：

- 证据来自哪里？
- 原文是什么？
- 在哪个条款 / span / 文件 / 版本？
- 该证据是否与当前争点相关？
- 该证据是否处于模型实际可见或系统实际检索到的范围？
- 是否存在反证？

**“这句话真的存在”只是最低门槛；“这句话与这个问题相关”才是可受理证据。**

## 第四条：程序正义

即使最终结果看起来合理，也不得通过跳过必需节点、伪造完成状态、静默吞掉失败、绕过 Review 或绕过 CI 来获得。

在 Agent-T 中：

> **一个正确但程序不可追溯的结果，不是可靠结果。**

## 第五条：人类保留最终责任

Agent-T 可以自动形成规则核查结果，但涉及合同签署、商业取舍、法律责任承担、真实交易行动时，最终决策责任仍由人类承担。

系统在不确定时应优先表达：
- 缺什么事实；
- 哪个证据没有闭合；
- 哪个判断依赖立场或商业偏好；
- 哪个结论只是 AI 意见。

# 第二章：权力分立

## 第六条：立法机关——Rule Governance

### 对应角色
维护者、领域专家、法务专家、Rule Pack、PR Review、CI、版本管理。

### 有权
- 新增、修改、废止规则；
- 修改规则类别与适用条件；
- 修改治理级 Prompt 与门禁；
- 调整正式流程，但必须通过评审与测试；
- 将经验证的 AI 重复发现沉淀为规则或测试。

### 无权
- 允许运行中的 LLM 自行修改 Rule Pack；
- 因一个个案“看起来特殊”而静默改变通用规则；
- 绕开测试与审查直接在生产环境改变正式裁决逻辑。

### 立法原则
任何规则变化都应至少包含：
1. 为什么改；
2. 哪类真实案例触发；
3. 改变哪些旧行为；
4. 新增或更新哪些测试；
5. 是否存在兼容性与误伤风险。

AI 可以**提案**，不能**颁布法律**。

---

## 第七条：法律——Rule Pack 与硬约束

Rule Pack 是“实体法”。

它定义：
- 哪些事实组合构成关注项；
- 哪些缺失构成 omission；
- 哪些规则属于 hardline / existence / heuristic；
- 哪些状态可以被异议层受理；
- 哪些输出属于禁止项。

规则必须可版本化、可测试、可追溯。

**规则不能因为某次 LLM 输出不同而临时变形。**

---

## 第八条：程序法——Graph / Pipeline / State Machine

LangGraph、Pipeline、状态机与事件语义属于“程序法”。

它们规定：
- 谁先执行；
- 哪一步必须完成；
- 哪一步可以失败软降级；
- 什么状态才能进入下一阶段；
- 什么时候才允许发出 `fully_complete`；
- 哪些错误必须显式标记为 unavailable / partial / failed。

程序法不得被“为了省一次调用”“为了 UI 更快”“结果反正差不多”等理由静默绕过。

**完成状态是法律语义，不是 UI 文案。**

---

# 第三章：调查权——公安 / 侦查系统

## 第九条：调查层的对应物

当前及未来包括但不限于：

- Parser
- Clause Index
- Quote Locator
- Retrieval
- Verify
- 文档解析
- 未来 RAG
- 多文档 Evidence Retrieval
- 用户补充事实的结构化采集

### 有权
- 定位原文；
- 查找关联条款；
- 提取金额、日期、主体、义务等事实；
- 构造候选证据；
- 标明未找到；
- 报告检索范围与覆盖限制。

### 无权
- 仅凭检索结果给出最终风险裁决；
- 把相似文本冒充当前争点的证据；
- 隐瞒“只检索了部分正文”；
- 将模型生成的引用当成真实原文；
- 自己决定法律适用结论。

调查系统负责回答：

> **“到底发生了什么？证据在哪里？”**

而不是：

> **“最终该怎么判？”**

---

# 第四章：公诉与证据审查权——检察系统

## 第十条：检察层的对应物

包括：
- Evidence Validation
- Quality Gate
- Candidate Admission
- Applicability Check
- Quote Verification
- Scope Validation
- 结构化输出校验

### 有权
决定某个 Candidate 是否具备进入正式异议 / 裁决流程的最低条件。

至少应检查：

1. **真实性**：quote 是否真的存在；
2. **定位性**：是否能映射到具体条款或 span；
3. **相关性**：是否支持当前 item / direction；
4. **可见性**：证据是否来自系统或模型实际看到的范围；
5. **完整性**：必要要件是否齐全；
6. **适用性**：规则类别、合同类型、立场和时间条件是否匹配；
7. **反证**：是否存在足以改变解释的例外或相反文本。

### 无权
- 因为 quote “是真的”就忽略它与当前争点无关；
- 用合同其他位置的真话给当前 Candidate “凑证据”；
- 代替 Rule Engine 修改正式结论；
- 为了让模型输出通过而降低门禁且不留记录。

**真实证据 ≠ 相关证据。**

---

# 第五章：审判权——法院与法官

## 第十一条：法院

“法院”是正式裁决过程，不等同于单一函数。

它接收：
- 可受理事实；
- 当前有效 Rule Pack；
- 明确的适用上下文；

并产出：
- 可追溯的正式状态；
- 适用规则；
- 主要证据；
- 必要的解释与限制。

## 第十二条：法官——Rule Engine / Checklist Engine

法官的核心职责是：

> **Fact + Applicable Rule → Formal Decision**

### 有权
- 依据 Rule Pack 给出正式 status；
- 确定主规则、缺项状态和明确的确定性结果；
- 拒绝不满足规则条件的正式判定。

### 无权
- 因用户立场改变客观事实；
- 因 LLM 的说法更“聪明”而覆盖规则；
- 在没有版本记录时改变判法；
- 将检索不到等同于现实中不存在，除非规则明确如此定义。

同一份输入、同一版本规则、同一确定性配置，应尽可能得到同一正式裁决。

---

# 第六章：辩护与异议权——AI 律师

## 第十三条：AI Objection Layer 的定位

AI 异议层不是“第二个法官”，而是**有边界的律师**。

### 有权
- 对 heuristic 的误报提出 false-positive 异议；
- 对 existence 的漏报提出 omission 异议；
- 找到例外、反证、等价表述或上下文；
- 指出原规则没有覆盖的真实问题；
- 生成解释、谈判问题和修改建议；
- 建议“这类问题应进入 Rule Pack”。

### 无权
- 直接改写 Rule Result；
- 修改服务端决定的 `rule_id`；
- 为自己扩大 Candidate 范围；
- 用候选范围外的证据给自己“洗白”；
- 把未验证 quote 当证据；
- 把“律师意见”展示成“法院判决”；
- 通过重复输出占满全局异议名额。

## 第十四条：一案一争点原则

原则上，一个 `(item_id, direction)` 是一个争点。

同一个争点可以拥有多条 evidence / counter-evidence，但不应仅因为模型换了六种摘句，就占据六个全局异议席位。

这条原则用于防止：
- 重复输出挤占其他争点；
- quota 被模型表达方式而不是业务问题消耗；
- UI 和人工确认被重复意见淹没。

---

# 第七章：当事人与立场

## 第十五条：Stance 的权力边界

Buyer / Seller、Tenant / Landlord、Discloser / Receiver 等立场决定：

- 对谁更不利；
- 哪个责任值得重点解释；
- 修改建议更偏向什么商业目标；
- 谈判策略如何表达。

Stance 不得改变：
- 合同原文；
- 数字；
- 日期；
- clause location；
- quote；
- 客观命中事实。

**立场影响评价，不改变事实。**

---

# 第八章：证据法

## 第十六条：Single Evidence Fact

一次确定性的风险命中，应尽可能产生一份稳定的 Evidence Record。

后续：
- 状态；
- quote；
- hits；
- primary clause；
- AI explanation；
- objection；
- Ask；
- report

应优先引用该 Evidence，而不是分别重新搜索、重新抽取、重新猜测。

> **一次风险命中，只产生一个证据事实；后面所有层都引用它。**

## 第十七条：证据必须带来源

理想 Evidence 至少包含：
- source/document id；
- version；
- clause id；
- start/end span；
- exact quote；
- normalized fact；
- producer；
- validation state。

多文档阶段还应包含：
- 文档优先级；
- 生效时间；
- 是否被补充协议覆盖；
- 权限；
- 证据冲突关系。

## 第十八条：覆盖范围必须诚实

如果系统：
- 只看了前 16k 字符；
- 只发送了 12 个 Candidate；
- 只检索了部分附件；
- 只加载了某些条款；

则必须显式记录 coverage。

不得把：

> “在我看到的范围内没有找到”

包装成：

> “合同中不存在”。

Coverage 是证据的一部分，不是调试信息。

---

# 第九章：卷宗、书记与审计日志

## 第十九条：State Store 的定位

SQLite / Review State / Evidence Chain / Audit Log 相当于卷宗与书记系统。

### 有权
- 保存状态；
- 保存证据；
- 保存规则版本；
- 保存人工确认；
- 保存 AI 异议；
- 保存失败与 coverage；
- 支持追溯。

### 无权
- 自己重算结论并覆盖上游；
- 丢失异议来源；
- 把“曾经出现过的 AI 文本”当成已经确认的事实；
- 在状态迁移时抹掉旧版本证据。

---

# 第十章：专家证人与外部工具

## 第二十条：专业工具只提供意见或事实

法律检索、搜索、计算器、OCR、外部数据库、专项模型、未来法规 Agent，均视为“专家证人”。

它们可以非常专业，但：

> **专业程度不自动带来裁判权。**

外部来源进入 Evidence Chain 前，应记录：
- 来源；
- 时间；
- 适用法域；
- 版本；
- 检索范围；
- 是否经过人工或规则确认。

---

# 第十一章：执行权

## 第二十一条：Execution 不得重新判案

Export、任务派发、通知、未来自动修改文档或工作流，属于执行层。

执行层只能基于**已经明确授权的状态**行动。

禁止：
- 在导出阶段偷偷改结论；
- 在发送任务时扩大风险等级；
- 在自动改合同前重新让模型自行决定“应该怎么判”；
- 在没有用户授权时实施不可逆外部动作。

---

# 第十二章：监督权——Tests / CI / Code Review / Audit

## 第二十二条：CI 不是装饰

CI 的职责不是“显示绿色徽章”，而是阻止未经程序验证的变化进入正式系统。

至少应保护：
- 核心规则回归；
- Evidence 映射；
- API schema；
- 类型与 lint；
- 前端关键流程；
- 安全与恶意输出边界；
- 已确认历史 bug 的 regression case。

## 第二十三条：Review 红灯不得被绿色 CI 抵消

如果 Code Review / 外部审计发现 P1/P2：

必须二选一：

1. **修复并增加必要回归测试；**
2. **明确记录 Accepted Risk：为什么暂时不修、影响范围、责任人 / 后续计划。**

禁止第三种状态：

> “知道，但什么也不写，CI 绿了就 Merge。”

高优先级未解决 review thread 应成为合并门禁的一部分。

---

# 第十三章：权力制衡

## 第二十四条：任何单一角色不得同时拥有完整链条

一个组件原则上不应同时完成：

> 找事实 → 判断证据有效 → 修改规则 → 作出正式裁决 → 执行外部动作

如果架构上必须合并实现，应在数据结构与接口上保持逻辑分权，并提供独立测试。

## 第二十五条：AI 不得自我授权

Prompt、模型返回值或模型建议不得成为扩大模型权限的依据。

例如模型不能通过输出：
- 新的 `rule_id`；
- 新的 Candidate；
- 更高 severity；
- “我认为应该直接修改状态”；

来获得服务端未授予的权限。

**Authority comes from code and governance, not from model text.**

## 第二十六条：Fail Closed 与 Fail Soft 的边界

治理关键项应倾向 **fail closed**：
- 非法 rule class；
- 未知正式状态；
- 不允许的权限组合；
- 无法验证的关键证据；
- 结构性配置错误。

用户体验或外部依赖可以 **fail soft**：
- LLM provider unavailable；
- AI objection unavailable；
- 非关键 enrichment 失败。

Fail soft 必须诚实显示“不可用”，不能伪装成“已检查且没有问题”。

---

# 第十四章：修宪与立法流程

## 第二十七条：什么属于“修宪级变化”

以下变化必须被视为高风险治理变更：

- AI 获得直接修改 Rule Result 的能力；
- 改变 Evidence 的事实来源定义；
- 取消人工确认边界；
- 改变 Rule / AI / Human 的优先级；
- 改变审计可追溯性；
- 允许运行时模型修改规则；
- 取消关键 CI / Review 门禁；
- 允许自动执行真实外部法律 / 财务动作。

这类变化必须显式在 PR 中说明“Constitution impact”。

## 第二十八条：普通立法流程

Rule Pack 或治理规则修改应遵循：

**发现问题 → 提案 → 复现 → 测试 → 实现 → Review → CI → Merge → Changelog**

AI 可以参与“发现问题、提案、生成草案、辅助测试”，但最终批准属于治理流程。

---

# 第十五章：开发团队执行清单

任何影响审查逻辑的 PR，作者与 Reviewer 至少回答：

### A. 角色
- 这次修改属于调查、检察、审判、律师、立法、书记、执行还是监督？
- 有没有让某个角色获得新的权力？

### B. 证据
- 新结论能否回到 exact quote / clause / span？
- 证据是真实且相关的吗？
- 是否可能引用模型未看到的文本？
- 是否诚实记录 coverage？

### C. 裁决
- 哪个字段是正式结果？
- AI 是否可能直接或间接覆盖它？
- 同样输入能否稳定重现？

### D. 程序
- Graph 顺序是否被改变？
- completion / unavailable / partial 语义是否仍然准确？
- 失败是否被静默吞掉？

### E. 测试
- 是否为新行为增加回归测试？
- 是否包含反例，而不仅是 happy path？
- 是否测试重复、截断、错误 scope、恶意模型输出？

### F. Review
- P1/P2 是否全部关闭或明确 Accepted Risk？
- 是否有 unresolved review thread？
- CI 通过是否真的执行了目标测试，而不是被 skip / feature flag 假绿？

如果这些问题无法回答，PR 不应被视为“只是一个小改动”。

# 第十六章：一个完整案例

假设采购合同出现：

> “设备到货后支付合同价款的 95%。”

Agent-T 的理想处理不是让一个模型从头说到尾，而是：

1. **公安 / 调查**：找到付款条款、验收条款、技术附件和可能的例外；
2. **检察 / 门禁**：确认 quote 存在、属于正确条款、证据范围有效；
3. **法官 / Rule Engine**：按现行 Rule Pack 形成正式 status；
4. **AI 律师**：提出“验收定义可能在其他条款”“技术附件有七日调试期”等异议；
5. **检察门禁再次审证**：AI 引用必须真实、相关、来自其可见范围；
6. **人类**：决定接受异议、修改合同、补材料或维持原判断；
7. **书记系统**：保存 Rule Result、Evidence、Objection、Human Decision 与版本；
8. **立法系统**：如果同类问题反复出现，提出 Rule Pack 改进 PR；
9. **监督系统**：用 regression test 保证未来不再退化。

这就是 Agent-T 的目标：

> **不是让 AI 获得无限裁判权，而是让不同能力在明确授权、证据规则与程序制衡下协作。**

---

# 结语：Agent-T 的真正实验

Agent-T 选择合同审查作为第一个垂直场景，但它真正探索的是一类更普遍的问题：

> **如何让生成式 AI 进入高价值决策流程，同时不让“智能”吞掉证据、规则、责任和程序。**

我们的答案不是减少 AI，而是建立治理：

**Rule of Law for Agents.**

规则不是为了束缚智能，而是为了让智能可以被信任、被审计、被纠正，也能够持续进化。
