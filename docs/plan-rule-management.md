# 规则管理专项：范围与交付顺序

日期：2026-11-08。用户要求将规则管理列为下一阶段重点，范围包括已有规则查看、编辑、启用/停用，定制规则新增、人工审核、自动化测试和正式上线。本文件为开发计划，非已实现功能，也不自动授权具体规则的法律结论。

## 目标与边界
让规则从「看得见」到「安全生效」形成可追踪流程。AI 只能辅助编写或解释，不能自行批准、发布或修改本次审查结论；规则和合同类型都须有明确适用范围。现有三类配置及技术服务清单为迁移基础，复杂匹配器不应伪装成可通过普通文本编辑的规则。

## 交付顺序
1. **盘点与只读规则目录**：按合同类型显示检查项、规则编号、说明、适用范围、当前状态、所属版本与维护来源；区分配置型规则和需程序支持的复杂规则。对现有清单建立可追溯基线，不改既有判定。
2. **草稿与变更申请**：支持提出新增定制规则、编辑、启用或停用；默认进入草稿，展示变更前后差异、规则编号、适用范围、设计理由及样例。规则“删除”优先软停用并保留历史；正式版本不可原地编辑。发布过程中单次审查固定使用同一不可变版本，执行、评分和版本记录须同源，禁止在途修改文件。
3. **评审与权限**：确定真实用户身份、规则编辑者、法务/专业审核者及发布者的分工；记录评审结论、理由、时间和版本。现有单据内临时提案只作输入，不得当成长期规则档案；长期保存的字段、脱敏、期限、权限、删除及合同证据引用须经过专门设计，不能绕过审查记录 TTL 静默保留原文。
4. **自动测试**：每条新规则提供正例、反例、边界和适用/不适用样例；运行配置校验、规则冲突/重复检查、既有全量回归与正式认可的金标合同集，明确预期变化和未经授权的变化。失败或缺少人工审批不允许上线。对 AI 生成内容、异常正则和运行预算设置边界。
5. **发布与回滚**：审核通过且测试成功后生成不可变版本及变更记录，发布前预览影响范围，由有权限人员明确执行上线；提供版本历史与可审计回滚，新旧审查保留各自版本标识，不自动改写历史结论。上线结果须以实际生产检查确认。
6. **客户定制和隔离**：基于真实使用场景确定客户规则与系统规则的覆盖、冲突、优先级、版本及访问隔离，不在无租户边界时把定制规则宣称为安全的多客户能力。

## 验收样例
- 法务可查看当前启用规则，提出一条定制规则，提交正反例，查看自动化检查和评审意见；测试或审批未通过不得发布。
- 停用一条规则后，新审查明确使用新版本；旧审查仍能追溯旧版本和当时结论；回滚后新审查使用回滚版本。
- 变更在一次长审查进行期间发布，运行、评分和留痕仍一致地使用该审查开始时冻结的版本。
- 不同客户的规则、文档和结果不可越权读取；审查记录过期后，规则审批保留的信息遵守已确定的隐私和留存政策。

## 前置事项与当前状态
目前规则仍由仓库 YAML 与代码维护，临时提案跟随审查数据过期，评审姓名未验证，尚无正式版本发布或用户/租户权限。先行完成本次版本验证和技术服务合同开放，再按上述顺序实施；具体耗时依首批规则数量、法务参与与权限方案核定，不以估计日期冒充排期承诺。
