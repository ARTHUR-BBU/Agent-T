# 账户、权限与规则审核：需求与安全边界

状态：开发中，2026-11-09。面向普通用户和管理员；先嵌入现有合同审查应用，不建设独立账户平台。个人身份是记录责任的门牌，服务端对具体资源的授权才是门锁。仅隐藏按钮、共享密码或用户自填姓名均不构成身份验证。

## 角色与操作

普通用户：登录、管理自己的会话、访问被明确授权的合同/报告/对话、创建并提交自己的规则草稿、查看自己有权查看的结果；不能管理账户、审批或发布。管理员：在被授权的工作区管理账户、审查规则候选、审批和明确发布/回滚；不因管理员身份默认读取所有个人合同。用户界面两类角色，后台仍分别检查账户管理、审核与发布权限，避免未来无法拆分。

规则生命周期：草稿 → 已提交、等待验证 → 待审核 → 审核通过/退回 → 发布；任何实际内容变更、基线变化或测试证据过期使旧审核失效。审核记录绑定系统认证用户 ID、候选完整哈希、测试证据、决定、理由及时间；发布者再次验证同一候选、基线和测试，原子切换并记录事件。用户已决定：管理员可以审核自己提出的规则；界面和审计须清楚显示提交人与审核人及是否为自审。普通草稿不能删除或降级硬性规则。

## 身份与数据边界

初始管理员只能经明确的本机/运维引导建立，禁止公开自注册和默认口令。采用成熟标准密码哈希和独立盐；密码不明文保存。登录应支持安全随机服务端会话、过期和撤销；账号停用或权限撤销后旧会话立即失效。生产会话必须走 HTTPS、HttpOnly/Secure/SameSite Cookie，并实施 CSRF token 与来源校验；本机 HTTP 只能做隔离测试。登录失败限速、密码重置、账户恢复和会话清理需有可测试的正式方案。

合同、附件、审查、报告、对话、异议及提案须逐对象验证所有权或明确授权；旧的无主记录不能静默归属新用户。现有 reviewer 自填姓名仅作为未认证历史说明，不可转化为新审批。规则草稿和审批信息按组织与职责控制，避免客户间泄露。审计记录与合同记录分离，最小化保存 ID、摘要、操作和决定，不复制原合同；保留期限和访问策略在上线前确定。

## 交付顺序与验收

1. 身份和权限的数据模型与威胁模型；本机隔离账户基础、双角色、独立审核与自动化测试。尚未接入时现有共享访问方式不变，不宣称具有多人隔离。
2. 受保护的登录/退出、后台逐请求鉴权与账户管理；凭据不进日志；用户停用或权限变化即时撤销会话。生产启用前 HTTPS、CSRF、防暴力尝试和恢复流程均须验证。
3. 合同及所有衍生接口按所有者或明确授权逐一隔离；对旧记录保留只读迁移策略并明确负责人。跨用户测试必须覆盖列表、详情、下载、对话、异议和附件。
4. 草稿归属、审核意见、不可变版本和发布审计；自动化测试覆盖伪造身份、越权、管理员自审留痕、篡改后旧审批失效、并发发布、回滚和旧审查保留原版本。
5. 完整集成、独立安全审查和真实人工验收之后再申请上线；本地试用/绿色 CI 不等于生产已安全就绪。
