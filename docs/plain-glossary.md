# 软件工程术语大白话手册（198 条）

> 给非技术背景的项目负责人查阅。比喻体系与成长日记一致（档案室/门禁/考试/账本/收银台）。
> 来源：Rohit Ghumare 推文清单（2026-10-18），用户要求逐条大白话化。

## 一、安全（防坏人）1-40

| # | 术语 | 大白话 |
|---|---|---|
| 1 | SQL注入 | 坏人在填表时夹带「指令」骗数据库执行——像在意见箱里塞一张写着「把箱子烧了」的纸，工作人员不辨真假照做 |
| 2 | XSS | 坏人在网页内容里藏恶意脚本，别的用户打开就被盗号——像公告栏被人贴了张带毒的贴纸 |
| 3 | CSRF | 坏人冒充已登录用户的手，偷偷替他发请求——趁你刷卡排队时，有人抓着你的手替他付款 |
| 4 | CORS | 浏览器的「跨家访问规矩」：A 网站的页面想调 B 网站的数据，B 得明确点头 |
| 5 | SSRF | 骗我们自己的服务器去访问它不该访问的内网地址——伪造门条让保安自己打开内部金库 |
| 6 | IDOR | 改一下网址里的编号就能看别人的单子——发票号从 1001 改成 1002 就能看到别人的发票 |
| 7 | 路径遍历 | 用 ../../ 这类符号让程序跳出允许的范围读别的文件——说「去档案室」结果一路走到馆长办公室 |
| 8 | 批量赋值 | 用户提交的表单里偷偷多塞几个字段（比如「我是管理员=true」），程序图省事全盘接收 |
| 9 | 点击劫持 | 在真按钮上面盖一层透明假页面，骗你点到「删除」——你以为点的是「确定收货」 |
| 10 | 内容安全策略 | 网站给浏览器的一份「只许执行我列出的内容」白名单声明 |
| 11 | 安全头部 | 网页响应自带的一组「防盗须知」标签，让浏览器自动开启各种防护 |
| 12 | 输入验证 | 所有用户填的东西先验明正身再用——门口先安检，不信任任何来料 |
| 13 | 服务端授权 | 权限判断必须在服务器做，不能只靠网页把按钮藏起来——藏按钮没用，金库锁得在金库上 |
| 14 | 行级安全 | 数据库自己保证「你只能查到你名下的行」——每个柜员只能开自己负责的抽屉 |
| 15 | 最小权限原则 | 每个程序/人只给刚好够用的权限——实习生不给馆长钥匙 |
| 16 | RBAC | 按角色分权（管理员/审核员/访客各一套权限）——工牌决定能进哪些门 |
| 17 | 密钥管理 | API 密钥/密码这类「钥匙」的存放、分发、更换制度——钥匙不能贴在大门上 |
| 18 | .env文件加入.gitignore | 配置文件（里面常有钥匙）不许进代码仓库——钥匙册不跟图纸一起复印外发 |
| 19 | API密钥轮换 | 定期换钥匙，旧钥匙作废——就算被偷过一把，损失也有时限 |
| 20 | 密钥扫描 | 自动检查代码仓库里有没有人不小心把钥匙提交上去 |
| 21 | 哈希 vs 加密 | 哈希=搅碎机（不可还原，用来验证「是不是原文」）；加密=保险箱（有钥匙可还原） |
| 22 | 密码加盐 | 存密码哈希前先掺一段随机料，让相同的密码也搅出不同的结果——防对照表反查 |
| 23 | bcrypt & Argon2 | 两种「故意搅得很慢」的密码哈希算法——慢是对 decryption（暴力破解）的防御 |
| 24 | JWT过期 | 登录凭证（令牌）自带有效期，过期必须重新验证 |
| 25 | 刷新令牌 | 正式凭证短命、换证凭证长命——门禁卡每天失效但可用长期工牌续办 |
| 26 | OAuth 2.0 | 「用微信/谷歌登录」背后那套授权标准——让别的平台证明你是你，但不把密码给它 |
| 27 | OpenID Connect | OAuth 之上的身份认证层——不只授权，还确认「这个人是谁」 |
| 28 | 会话固定 | 坏人提前把登录后的凭证号塞给你，你一登录他就用同一凭证——凭证号必须在登录时换新 |
| 29 | MFA | 多因素认证：密码之外再加手机验证码/指纹——两把锁 |
| 30 | 暴力破解防护 | 限制试错次数+延长等待——密码箱连错三次锁半小时 |
| 31 | 账户枚举 | 登录页对「密码错」和「无此用户」给不同提示，等于帮坏人确认哪些账号存在 |
| 32 | 计时攻击 | 靠「响应快慢」猜密码——对比对的字符越多响应略慢，慢 zero.x 秒也是线索 |
| 33 | 文件上传验证 | 用户传的文件先验类型/大小/内容——收包裹要开箱检查，不能只看面单 |
| 34 | Webhook签名验证 | 别人推送给我们的通知要带防伪签名，验证是我们授权方发的 |
| 35 | TLS证书过期 | 网站的「防窃听证书」过期后浏览器会警告——门禁系统的年检标签 |
| 36 | HSTS | 强制浏览器只走加密通道访问我们——「本店只走VIP加密通道，请勿走明文道」 |
| 37 | 静态加密 | 存在硬盘上的数据本身也是加密的——档案柜上锁，不只门口有保安 |
| 38 | 依赖项漏洞 | 我们引用的第三方组件自带安全洞——装修工带来的电线是次品 |
| 39 | 供应链攻击 | 坏人污染上游组件，全线中招——面粉厂被下毒，所有面包房遭殃 |
| 40 | 威胁建模 | 动工前先系统想「坏人会从哪进来」——画一张「小偷路线图」逐条设防 |

## 二、数据库（档案室）41-60

| # | 术语 | 大白话 |
|---|---|---|
| 41 | 索引 | 给档案柜加目录页——翻档案不用一本本翻，先查目录直达 |
| 42 | EXPLAIN ANALYZE | 让数据库「说出」它查一条数据的完整路线——看目录是怎么用的，找出慢在哪 |
| 43 | N+1查询 | 查 100 条记录却额外发了 100 次小查询——本可一次取一箱，结果一颗颗跑 |
| 44 | 全表扫描 | 没有目录可用，只能一本本翻完整个档案室——数据多时慢如蜗牛 |
| 45 | 连接池 | 提前备好一摞「数据库通行证」循环使用——不用每次办事都重新办证 |
| 46 | 数据库迁移 | 结构变更（加字段/建表）的版本化脚本——档案室的「装修施工单」，可追溯 |
| 47 | 回滚迁移 | 装修装错了能按施工单倒回去复原 |
| 48 | 事务 | 一组操作要么全成、要么全不算——转账「扣你钱+加我钱」必须捆绑 |
| 49 | ACID | 事务四原则：全成全不算、账目前后守恒、互不干扰、落账不丢 |
| 50 | 隔离级别 | 同时办事的人互相「干扰程度」的档位——越严格越安全但越慢 |
| 51 | 死锁 | 两个人各拿着对方要的钥匙互相等——谁也走不了 |
| 52 | 乐观锁 | 假设没冲突，保存时才发现被人改过就重来——交表时发现版本号旧了就重新填 |
| 53 | 悲观锁 | 先把档案锁上再慢慢看——别人干等但绝不冲突 |
| 54 | 规范化 | 数据不重复存（客户电话只存一处，别处引用）——一本台账管到底 |
| 55 | 反规范化 | 故意存点重复数据换查询速度——前台多贴一份常用电话表 |
| 56 | 外键 | 表与表之间的「引用关系绑定」——引用的合同号必须在合同册里真实存在 |
| 57 | 唯一约束 | 某列不许出现重复值——身份证号一栏不许两人同号 |
| 58 | 级联删除 | 删主记录时自动删掉关联记录——销户时名下关联单据一起处理 |
| 59 | 软删除 | 只打「已删除」标记不真删——档案进碎纸机前先进「作废」筐，可追溯 |
| 60 | UUID vs 自增 | 随机长编号 vs 按顺序编号——随机编号不怕被猜（安全+多机房不撞号），顺序编号直观但可预测 |

## 三、数据库进阶与分布式 61-89

| # | 术语 | 大白话 |
|---|---|---|
| 61 | 基于游标的翻页 | 翻页不用「第 N 页」而用「从上一页最后一条往后」——书签法，翻再深也不乱 |
| 62 | 全文搜索 | 不只按编号查，还能按「内容里的词」查——档案室配了全文检索机 |
| 63 | 只读副本 | 正本之外抄几份只供查阅的副本——查档案的人去副本柜，别挤坏正本 |
| 64 | 复制延迟 | 副本抄写需要时间，刚发生的改动副本上可能还没看到 |
| 65 | 分片 | 数据按规则拆到多个柜子——A-M 档案一柜、N-Z 一柜 |
| 66 | 分区 | 一个柜子内部分隔层——便于整层归档/清理 |
| 67 | 热点分区 | 某一层被翻得特别勤，成了瓶颈——大家都挤同一层 |
| 68 | Postgres VACUUM | 数据库的「定期大扫除」——清理删掉档案留下的空位碎片 |
| 69 | 物化视图 | 提前算好存起来的统计报表——月报提前算好贴墙上，不用每次现算 |
| 70 | 备份 | 定期把整个档案室复印存别处 |
| 71 | 测试恢复 | 光备份不够，要真的演练「从备份恢复」——复印本拿出来真能用才算数 |
| 72 | 定时恢复演练 | 按计划做恢复演习，不让备份变成摆设 |
| 73 | 变更数据捕获 | 把「每一笔改动」实时记录广播出去——流水账同步给分店 |
| 74 | 出箱模式 | 用一张「待办表」保证要发出去的通知至少发一次且不乱序——前台登记外发件 |
| 75 | ORM延迟加载 | 引用的关联数据等到真用到才去取——先拿合同，附件等打开时再取 |
| 76 | CAP定理 | 分布式系统三选二：数据一致、随时可用、容忍断网——不可能三全 |
| 77 | 最终一致性 | 短暂不一致没关系，保证过一会儿大家对齐——分店账目稍后与总店对平 |
| 78 | 强一致性 | 任何时刻所有人看到的都是同一份数据——绝对同步，代价是慢 |
| 79 | Raft共识 | 多台机器商量「谁是主、记录对不对」的民主表决协议 |
| 80 | 领导者选举 | 主机器挂了，剩下的投票选出新主——接班机制 |
| 81 | 分裂脑 | 两台机器都以为自己是主，各记各的账——灾难级故障，必须防止 |
| 82 | 法定人数 | 表决要过半数才有效——3 台里至少 2 台同意才算数 |
| 83 | 时钟偏差 | 不同机器的钟不完全一样快——分布式系统里「几点几分」不可全信 |
| 84 | 分布式锁 | 多台机器抢同一个资源时的「全局排队号」 |
| 85 | 一致性哈希 | 数据增多时只搬最小量的数据——新柜子加入时只分走邻柜一小摞 |
| 86 | 布隆过滤器 | 一个「绝对没有、可能有过」的超省内存快速筛查器——先过滤掉 99% 不用查的 |
| 87 | 两阶段提交 | 先问所有分店「能执行吗」再统一下令执行——保证全成全不算 |
| 88 | CQRS | 「写账」和「查账」分成两套系统各优化各的 |
| 89 | 事件溯源 | 不存「当前状态」而存「全部操作流水」，状态靠重放流水算出——账本记流水不记余额 |

## 四、稳定性与流量 90-107

| # | 术语 | 大白话 |
|---|---|---|
| 90 | 竞态条件 | 两个请求同时读写同一数据导致错乱——两人同时抢最后一个号 |
| 91 | 背压 | 下游消化不了就告诉上游「慢点发」——工厂堵了就减送料 |
| 92 | 负载卸载 | 太忙时优先丢弃低价值请求保住核心业务——先拒散客保大客户 |
| 93 | 隔离舱壁 | 各模块资源隔离，一处沉不拖全船——轮船的分仓水密隔间 |
| 94 | 抖动 | 重试/调度的时间点故意加随机偏移，避免大家同一秒挤兑 |
| 95 | 重试风暴 | 服务刚恢复就被积压的重试淹死——店门一开挤进比原来更多的人 |
| 96 | 级联故障 | 一个环节倒下拖垮上下游——高速路一个事故堵死整条线 |
| 97 | 惊群效应 | 门一开所有人同时冲——定时任务同一秒齐发打爆系统 |
| 98 | 缓存失效 | 缓存里的数据到期/被清，只能回数据库现取 |
| 99 | 缓存命中率 | 请求里有多少直接从「快手柜」拿到——越高越省越快 |
| 100 | TTL | 缓存数据的保质期——到期的速食下架 |
| 101 | 缓存预热 | 开门前先把热门货摆上快手柜——避免开门瞬间全回数据库挤兑 |
| 102 | 直写 vs 回写 | 写数据时同步更新缓存（稳）vs 先写库后刷缓存（快但有丢的风险） |
| 103 | Redis淘汰策略 | 快手柜满了按什么规矩清位（最近最少用/最不常用等） |
| 104 | CDN | 全国各地的内容分发点——用户就近取货，不用都回总仓 |
| 105 | Cache-Control头部 | 网页告诉浏览器和中间节点「这份内容能存多久」 |
| 106 | ETags | 内容指纹：没变就返回「没变」三个字省流量 |
| 107 | 死信队列 | 处理失败的通知先进「待查件」筐，不丢也不堵正常件 |

## 五、消息与通信 108-127

| # | 术语 | 大白话 |
|---|---|---|
| 108 | 毒消息 | 一条怎么处理都失败的通知，会反复卡住处理流程——必须隔离 |

| 113 | 分区键 | 按「哪个客户/哪条业务」决定包裹进哪个通道——同客户的件进同一道保证顺序 |
| 114 | 后台任务 | 不用当场等结果的事（发邮件/生成报告）丢给后台慢慢干 |
| 115 | Webhook重试 | 通知发失败自动再试——按间隔递增地补发 |
| 116 | DNS | 互联网的「电话簿」：域名翻译成机器地址 |
| 117 | DNS传播 | 电话簿更新后全世界同步需要时间——换地址后有人还打旧号 |
| 118 | HTTP状态码 | 每个响应的三位数字暗语：200 办好了/401 没凭证/404 没这页/500 我这边出错了 |
| 119 | HTTP方法语义 | GET=只看不动、POST=新建、DELETE=删除——动作要对号 |
| 120 | 保持连接 | 一次握手多次复用通道——办多件事不用反复排队进门 |
| 121 | HTTP/2 | 通道升级版：一趟车拉多件货、头信息压缩 |
| 122 | WebSocket | 双方建立常连通道，谁有话随时说——对讲机 vs 寄信 |
| 123 | 服务器发送事件 | 服务器单向持续推送（比如进度条更新） |
| 124 | 长轮询 | 客户端问一次、服务器拿着不回直到有新货——半实时的笨办法 |
| 125 | gRPC | 服务之间的高速专线通话协议（二进制、快、带合同校验） |
| 126 | 协议缓冲区 | gRPC 用的紧凑数据格式——比 JSON 省一半以上流量 |
| 127 | API版本控制 | 接口升级保留旧版并行——老客户用 v1，新客户用 v2，不强制一起换 |

## 六、网络与基础设施 128-152

| # | 术语 | 大白话 |
|---|---|---|
| 128 | OpenAPI规范 | 接口的「说明书标准格式」——机器也能读懂我们能干什么 |
| 129 | 向后兼容 | 升级后老用法照常能用——老钥匙在新锁上也能开 |

| 137 | 防火墙 | 网络门禁：哪些流量许进许出 |
| 138 | 安全组 | 云上按机器绑定的门禁规则组 |
| 139 | 服务网格 | 服务之间通话的统一「总机+安检层」 |
| 140 | 入口控制器 | 外部流量进集群的总大门+分诊台 |
| 141 | 健康检查 | 定期戳一下每个服务「还活着吗」 |
| 142 | 存活 vs 就绪探针 | 活着（死了就重启）vs 能接客（没准备好就先别派单） |

| 145 | 无状态服务 | 服务自己不存客户数据，谁都能接任何单——随时可换人 |
| 146 | 故障转移 | 主机挂了备用机自动顶上 |
| 147 | 多区域 | 服务分布在多个地理机房——一个机房断电不影响 |
| 148 | 可用区 | 同一地域内的独立机房（独立供电网络） |
| 149 | 单点故障 | 某个环节只有一份，它挂全挂——唯一的那把钥匙丢了就全锁死 |
| 150 | 灾难恢复 | 大灾（机房全毁）后重建业务能力的预案 |
