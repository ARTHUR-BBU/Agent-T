## 一、裁定要旨（给所有同事的大白话版）

从阶段 3 起，Agent-T 的每条检查项都挂一个「身份标签」，叫 class，共三种：

- **hardline（铁律线）**：这条线背后是法条或法定红线，命中就是客观风险。AI 对结果提的任何异议，一概不送审——但报告侧可以**解释**条款具体后果。
- **existence（存在性）**：这条检查的是「合同里写了没有」。AI 只有说「合同里其实用了别的写法写了，但词表没认出来」（漏报）才送审；AI 说「缺了也没关系、不该标」（想把缺项洗成通过），不送审。
- **heuristic（启发式）**：这条判断的是「合理不合理、均衡不均衡」，本身有裁量空间。AI 说「这条标重了」（误报）可以送审；AI 说「还有别的写法没标到」（漏报）不送审——那属于金标建设，不是异议层的事。

一句话总结：**异议层受理 ≠ 改判**。受理只是把候选送交专业人复议，复议结论只有两种——维持原判，或发起第六节的修订通道。

## 二、三分法的法理依据与边界

### 2.1 hardline：只解释、永不受理异议

**法理**：hardline 簇的判定标准来自外部法源（司法解释、民法典强制性规定与法定默认安排），不是来自我们的词表。异议受理机制的存在前提是「规则可能有错、LLM 能指出错在哪」；而法条的效力评价不因措辞变换而改变——背靠背条款不因为写成「以业主回款为准」就不是背靠背（法释〔2024〕11 号），单方免除违约责任不因为写成「双方互不追究」就变得对等。

三点具体理由：

1. **效力性强制性规定无解释空间**。法释〔2024〕11 号对背靠背条款的「无效」评价、民法典 497 条对不合理免责格式条款的效力控制，是法律对条款效力的否定性评价，不是商业合理性裁量。允许异议等于允许把法定风险洗成「通过」，这是产品责任层面的红线。
2. **「误报」概念在铁律线上不成立**。铁律词表已经过多轮对抗校准（背靠背三组正则、押金没收的 unless 客体绑定、「逾期视为合格」不设豁免等），每组均配有对抗样例。LLM 提出的「误报」候选，经核查几乎均为措辞变体命中，恰是对抗校准的目标而非错误。
3. **漏报扩张必须由专业人对照法条类型后走修订通道**。铁律漏报（某类法定风险写法没被词表覆盖）的兜底靠金标回归与修订通道，不能由运行时 LLM 自行认定「这也是背靠背」——法源覆盖面的扩张是法律判断，不是文本匹配判断。

**「只解释」的边界**：报告层可以（且应当）解释铁律条款的具体后果、涉及法条、对当事人各方的含义；唯独不能通过任何机制改变「需关注」的判定本身。

### 2.2 existence：只受理漏报异议

**法理**：存在性项回答的是「写了没有」，风险本体是「缺」。要件缺失（缺签署、缺适用法律、缺主体信息）的法律后果是客观的：民法典 490 条下签署要件影响合同成立时点；涉外法律适用必须明示选择（涉外民事关系法律适用法第 3 条）；主体信息缺失影响责任主体的可识别性。

- **漏报为什么收**：存在性项最真实的缺陷就是词表覆盖不全——民法典 490 条明文承认签名、盖章、按指印三种等价签署方式，租赁回放校准实证了「签名/按指印/签字后生效」等十余种等价写法。合同用了等价写法而词表没认出来，导致误标「缺失」，这是可验证、可修复的词表问题，LLM 的漏报候选恰好是词表校准的素材，受理后走词表修订。
- **误报为什么不收**：对存在性项提「误报」，LLM 的论证方向几乎必然是「这个缺项其实不要紧」——「只写管辖就够、适用法律不用写」「没盖章但电子签了」「主体信息不重要」。这正是 NDA 红线明确封死的洗白路径（缺适用法律仅有管辖不够、缺签署印章不得通过）。受理这类候选等于给红线开洞。

### 2.3 heuristic：可受理误报异议

**法理**：启发式项的判定标准是合理性权衡——预付周期多长算过长、宽限期几天算过短、违约后果与违约程度是否失衡。这类判断有真实裁量空间，规则确实可能标重（例如按未履行部分 20% 计违约金是合理约定，曾因词表过宽被误捕，最终靠 unless 修复）。误报候选送专业人复议，是成本最低的质量反馈回路。

- **漏报为什么不收**：本项目铁律是「漏报比误报危险，规则宁可多提示」。启发式项的多提示是设计意图而非缺陷；LLM 提「还有别的风险写法该标」属于金标样例与对抗集建设事务，走金标通道，不占异议层资源。

### 2.4 边界总原则

两个开口（existence 的漏报口、heuristic 的误报口）共同点：**把「可能错」交给专业人复核，而不是交给 LLM 定案**。LLM 在异议层只生产候选，永不生产结论。

## 三、class 优先级与特殊状态裁定

1. **优先级**：规则级 `class`（命中规则自带）> 簇级 `class` > 默认 `heuristic`。判定异议按「实际命中那条规则」的 class 走，不按簇级兜底值走。
2. **`na: true` 簇不参与异议层**：本类不适用项无判定输出，无异议对象。LLM 若对 na 提异议（如「这份 NDA 约定了服务费，价款项该审」）一律不送审——那是品类分诊问题，走预审分诊台。
3. **`missing_as: 需关注` 簇**（如 NDA governing_law、signature）：缺失判定同样受 class 约束，方向矩阵照常适用。
4. **引擎只读**：class 是引擎读取的元数据，运行时（API、报告层、LLM 提示词）不得覆写，详见第六节红线。

## 五、受理规则总表（class × 异议方向矩阵）

| class \ 异议方向 | 误报异议（false_positive：标注了不该标） | 漏报异议（omission：该标没标/写法没认出） |
|---|---|---|
| **hardline** | **不送审** | **不送审**（只解释，永不受理） |
| **existence** | **不受理** | **受理** → 送专业复议 |
| **heuristic** | **受理** → 送专业复议 | **不受理** |
| **na: true** | 不适用（无判定输出，异议层 N/A，一律不送审） | 不适用（同左） |

三条配套规则：

1. **受理 ≠ 改判**：受理仅生成复议工单；复议人（法务侧）结论限于「维持原判」或「发起修订通道」，不得在工单内直接改写判定结果。
2. **规则级 class 优先**：命中规则自带 class 时按规则级走（如 payment 簇命中背靠背规则按 hardline 不送审，命中支付节奏规则按 heuristic 可收误报）。
3. **分诊类异议不进异议层**：对 na 状态、品类归属、立场不可审的异议，一律回预审分诊台，不占用异议层。

## 六、修订通道（class 变更的版本化）

参照铁律 3 的版本化先例执行：

1. **提案**：任何一方（含对 LLM 异议候选的统计分析结论）认为某簇 class 应变更，须提交 class-change 提案，内容至少含：簇 id、现 class、拟 class、法理依据（法条/惯例/案例类型）、对金标与对抗样例的影响面评估。
2. **复议**：由法务老钱复议并出具裁定补录（本文档追加修订节，不删史），说明变更理由与对抗样例如何随之调整。
3. **落库与回归**：YAML class 变更与金标/对抗集同步修改，全量回归并附 git 提交哈希（按门禁回归哈希纪律）；门禁窗口内冻结工作区改动。
4. **版本记录**：各 checklist 文件头登记 class 版本号与修订日期，历史判定可追溯。
