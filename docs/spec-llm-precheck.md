# Spec：LLM 预审（合同分类 + 支持性判断）

> 状态：v2（已并入法务老钱分类金标裁定 2026-09-09；待小智娘测试计划 + 肉饼红线评审）
> 提出人：用户（2026-09-09，实测发现服务合同按采购清单硬审产出荒谬结论）
> 负责人：开发狗

## 1. 背景与问题

当前流水线：用户上传时自选品类 → 规则清单逐条审 → LLM 参考评分。
系统**无条件信任用户选的品类**。用户在「采购」下传了一份「AI 故事视频
制作服务合同」，系统硬审，产出「未找到标的 / 缺价款与支付约定」——
看似专业，实则文不对题（垃圾进、垃圾出，且穿着专业外衣）。

## 2. 目标

上传后、审查前插入 LLM 预审环节：

1. **识别**：这是什么合同（输出类型判断 + 依据）
2. **判断支持性**：我们是否支持该类型；不支持 → 明确告知支持列表，绝不硬审
3. **对账**：与用户所选品类不一致 → 提示用户确认切换，**不静默切换**
4. **预判底稿**（二期）：预审摘要进入评分上下文，让参考分更有依据

## 3. 方案

### 3.1 流水线变化

```
upload → extract_text → [NEW] precheck → 对账分支 → run_checklist → ...
```

precheck 同步执行（v4-flash 单轮实测 2-3s，上传仍秒回量级；
异步审查机制不变）。

### 3.2 precheck 模块（app/services/precheck.py）

- 输入：合同全文（clip 到 ~3000 字，分类不需要全文）
- 输出（Pydantic Schema 校验，禁止裸 json.loads）：

```json
{
  "detected_type": "服务合同（视频制作类）",
  "is_supported": false,
  "suggested_category": null,
  "confidence": "high | medium | low",
  "summary": "一份委托制作短视频的服务合同，核心义务是交付成片…"
}
```

- 供应商链复用 llm_ask（DeepSeek > 智谱 > xAI）；无 Key 或调用失败 →
  **降级跳过预审**（见 3.5），流程照旧
- 提示词进 `app/prompts/`（提示词管理约定），输出 JSON + Schema 校验，
  解析失败重试一次，再失败降级

### 3.3 对账分支（已按老钱裁定修订）

| 情形 | 行为 |
|---|---|
| 检测=所选 | 照旧开审 |
| **不支持** | 返回 `category_confirm` 响应（不开 review），文案必须含三要素：① 明说「未生成报告」；② 显式否定「未审查=无风险」；③ 给支持列表（老钱第三节候选文案，九哥润色后定稿） |
| 支持但不一致（high/medium） | 返回 `category_confirm` + 建议品类，前端二选一；用户确认后带最终品类重新进入审查。不支持类型**不给「切换」选项**，直接走不支持文案 |
| **low 置信度但 LLM 有倾向且 ≠ 所选**（老钱改判） | **照旧开审，不阻断**，但在报告头部加一行非阻断提示：「品类存疑：按{所选}清单审查，检测倾向{检测}（把握较低），结论请结合文件实际类型阅读」——知情权不能省，打断权必须不给 |

老钱裁定依据：low=静默的方案会系统性地对最难分类的文件（混合、非标、
无标题）制造漏报，与全项目「漏报优先于误报」基本盘相反；而阻断会把
LLM 从「选尺子的」变成「裁判」，违反红线。

### 3.3.1 分类金标要点（完整裁定见老钱意见书，此处钉死实现要点）

- **判定顺序固定**：NDA → 租赁 → 采购 → 其他（不支持）。采购是兜底桶放最后
- **视角是品类定义的一部分**：租赁=承租方、采购=买方、NDA=接收方。
  卖方视角的销售合同 → 不支持（结论全部反向，比不支持更危险）
- **服务采购 vs 服务合同的分界式**：标的能写成「型号/数量/规格参数」→ 采购；
  标的写成「方案/作品/系统/成片」+ 有知识产权归属条款 → 服务合同，不支持
- **混合合同**：按主给付义务定性；主次分不出 → 不支持，绝不按所选硬审
- 转租 → 归租赁；带维护条款的设备租赁 → 归租赁；框架采购（无金额）→ 归采购；
  劳动/借款/股权/无偿借用 → 不支持

### 3.4 红线兼容性论证（供肉饼评审）

- 分类/路由 ≠ 裁判：LLM 决定「用哪把尺子」，档位仍 100% 出自
  run_checklist；预审结果**永不写入 items/status**
- 预审 summary 若展示，标注「AI 预判」并走禁语清洗
- 降级路径（无 Key/解析失败）退回现状，规则审查可用性不受影响——
  预审是增强不是依赖（此为 fail-open，特此声明请肉饼裁决是否接受）

### 3.5 降级矩阵

| 情形 | 行为 |
|---|---|
| 无 LLM Key | 跳过预审，照旧开审 |
| 调用超时/异常 | 即降级，**不重试**（实现如此且更省调用费；解析失败才重试 1 次） |
| 预审并发槽占满 | 同上（busy 降级，不排队） |
| JSON 解析失败 ×2 | 同上 |
| 置信度 low 且无倾向差异 | 静默照旧 |
| 置信度 low 但有倾向差异 | 见 3.3：照旧开审 + 报告头非阻断「品类存疑」提示 |

### 3.6 结构性修复（老钱附赠发现）

`app/services/checklist.py:38-39` 的 `load_checklist` 在品类配置不存在时
**静默 fallback 到 procurement**——正是本次事故的结构性温床。本次改造：
precheck 生效路径上未知品类显式走 category_confirm；fallback 保留但必须
打 warning 日志。

## 4. 影响范围

- `app/api/routes.py`（upload 分支）、`app/api/schemas.py`（响应模型）
- 新增 `app/services/precheck.py` + `app/prompts/precheck.py`
- 前端 `app.js`（category_confirm 交互）
- 测试：precheck 单测（mock LLM）+ 跨品类对抗集（小智娘）+ 全量回归

## 5. 验收标准

1. 服务合同传采购：用户收到「暂不支持/建议切换」提示，**不产出错误报告**
2. 正确品类：行为与现状完全一致（预审不增加误打扰）
3. 无 Key 环境：行为与现状完全一致
4. 全量测试绿 + 对抗集通过率达标（标准由小智娘定）
5. 老钱金标案例全数命中

## 6. 二期（本 spec 不实现）

- 预审 summary 进评分提示词
- 支持新品类（服务合同等）——老钱评估清单可行性后另行立项
