新增 `app/services/migration_inspection.py`：通过 SQLite backup 在系统临时目录分别复制账户库与合同库，在副本中检查 SQLite quick_check、核心表和部分关键列、未知表及视图数量、进行中的规则测试、无效合同 JSON、进行中的合同和已有归属合同数量。它不会建立迁移目标或导入数据，恒返回 `migration_ready=False`。正常返回值不包含合同或账户行内容，也不暴露未知对象名称。单库 WAL 场景只用合成数据测试。

独立审核指出临时副本包含合同与凭据散列，受系统临时目录 ACL 约束，异常退出可残留，删除不等于安全擦除；返回值与函数说明均已明确。共享 deadline 和 SQLite progress handler 只是尽力超时，不是进程级硬终止。只读 SQLite 连接可能涉及 WAL sidecar，文件系统级零写入尚未验证；不得在真实敏感数据上直接运行作为迁移验收。

新增 `app/services/account_review_migration.py`，仅作为未接入 API/CLI 的**合成数据迁移实验**：从受信任代码生成参考 schema，拒绝未知或缺少对应保护对象的源 schema；以 SQLite backup 分别取得快照，在新目标导入时保留 rowid，逐表比较数据摘要，旧会话不复制，历史合同 owner 置空；验证部分规则摘要、审批/测试绑定、合同引用和关联草稿关系。复制到发布期间持有两库 SQLite 写锁；发布时将含 `agent-t.sqlite` 的新目录作为整体原子发布（Windows 不覆盖 rename；Linux 使用 renameat2 的 NOREPLACE；其他平台拒绝），不接受已有目标目录。独立审核发现并推动修复缺失触发器、伪装 SQLite 保留名、缺失测试结果和旧版目标 sidecar 发布竞争等问题。

**不能用于真实数据或正式切换**：参考结构仍依赖当前本机 Python、代码和依赖目录可信；双库 SQLite 锁仅约束遵循 SQLite 协议的写入，锁释放后旧后台任务仍可写旧库，调用者声明停服不等于工具强制停服；临时敏感副本可能残留。暂存目录的私有 ACL 尚未强制，独立审核复现了可写进程在最后目录检查后、原子发布前插入 sidecar 的竞争；也不能防止该进程改写数据库。最后检查只拒绝发现时已经存在的额外文件和符号链接，不能防止硬链接替换或后续竞争。目录 rename 也未经断电持久性和发布后清理失败恢复验证。SQLite 锁/sidecar 可能改变源目录文件状态，不能声称文件系统零写入。严格 schema 比对会拒绝某些旧版本或正常的 `sqlite_stat1` 统计表，需明确兼容策略，不能静默丢弃。尚未完成发布事件链等全部业务语义检查、维护窗口强制、崩溃/磁盘满恢复、多进程对抗和真实库演练。旧源库会话仍能被旧进程使用；新库清空会话不自动关闭旧服务。合同接口及后台任务授权、旧档案认领也未实现。原先建议直接备份账户库作为目标已由独立审核撤回：未经严格验证会复制不可信 schema。
