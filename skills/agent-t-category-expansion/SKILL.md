# Agent-T 新品类施工

## 目标

把新品类做成可审、可复核、可回退的最小能力，而不是复制一轮无限加固。

Agent-T 的正式结论仍由规则引擎产生。模型只能做建议、发现疑点或帮助分诊；它不得静默改品类、改规则状态或代替人工确认。

## 先定位，再开工

1. 阅读 `docs/roadmap-master.md`，确认新品类在总路线图的位置、当前主线门槛和允许并行的工作。
2. 明确本批只解决什么：品类边界、检查项、解析缺口、模型建议或正式开放。把其余事项登记为挂账，不夹带进来。
3. 选施工轨道：
   - **最小轨道**：复用现有解析、规则形态和已裁定口径的品类扩展。完成边界说明、法务清单、最小金标、规则/测试、回归门禁。
   - **完整轨道**：出现新的法律口径、新文档形态（如表格/附件）、新模型调用、正式对外开放或跨品类状态变化时，补做独立留出集、对抗集、生产受控验收。

不要因为新品类就自动引入新模型、平台化留痕、权限系统或长期运营机制。

## 每个新品类的最小闭环

### 1. 边界与法务口径

- 说明什么合同收、什么合同拒收或转人工；相邻品类如何区分。
- 由法务为每个检查项给出：命中条件、空白/悬置/否认时的状态、是否需要旗标、例外和适用立场。
- 裁定未到前，不写会改变正式状态的规则代码。

### 2. 语料与金标

- 采用可追溯语料：记录来源、文件哈希、解析方式和金标责任人。
- 明确真实合同、公开示范文本和合成对抗样例，不能把模板成绩包装成真实泛化能力。
- 新品类至少要有正例、反例、边界例和空白/悬置例；对抗例用于防回归，不替代真实语料。
- 若生产解析与本地提取不同，先做同构提取再标注；不能拿不同文本形态的成绩作结论。

### 3. 规则与测试

- 先用原型或靶向测试复现，后改 YAML/匹配器；规则只覆盖已裁定的形态。
- 新增项必须写出状态断言与证据断言；空栏、否认、相邻普通语句、跨行/跨格等已知混淆面按需加入。
- 对存量语料做逐项比较。允许的翻转必须写成精确白名单（文件、检查项、旧状态、新状态）；不使用只看总数的门禁。
- 保持“最小修复”：没有具体失败证据，不顺手改词表、抽取器或其他品类。

### 4. 合并、部署与开放

- 合并、部署、生产证据重导、移除 hidden 开关是四个不同动作，分别报告和授权。
- 部署前备份必要账本，运行安全门；部署后用受控样本验证新增分支、相邻正例和既有不一致确认分支。
- 正式开放前，确认用户界面、默认行为、拒收/人工确认和生产留痕都与设计一致。
- 发布后把明确缺口加入观察集；不要把“可能更好”的想法自动变成下一批工程。

## 模型和 System 1 的额外条件

仅当新品类要接入模型建议或改变分诊台时，阅读 [模型分诊与上线门](references/model-triage-and-release.md)。

模型建议必须可关闭、受预算约束、可留痕。所有模型建议与用户选择不一致时，必须由用户确认；模型置信度是路由信号，不是正式法律结论。

## 收官输出

交付时给出一张短表：已完成、证据（测试/CI/生产）、未验证边界、挂账和下一道门。更新 `docs/roadmap-master.md`，只登记已经合并、部署或实证的事实。

如需完整模板、门槛与反例清单，阅读 [新品类施工门与交付模板](references/category-delivery-gates.md)。
